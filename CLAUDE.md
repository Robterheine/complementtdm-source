# CLAUDE.md

Behavioral guidelines for coding agents working on this repo. Adapted from
[andrej-karpathy-skills](https://github.com/multica-ai/andrej-karpathy-skills)
(MIT) and merged with this project's own conventions — see `docs/DEVELOPER_GUIDE.md`'s
numbered golden rules (§2) for the project-specific rules these generalize.
Where the two overlap (e.g. rule 4 below and golden rule 7b), the README's
version is the authoritative, more specific one; this file is the general
discipline underneath it.

**Tradeoff:** these guidelines bias toward caution over speed. For a truly
trivial change, use judgment.

## 1. Think before coding

Don't assume. Don't hide confusion. Surface tradeoffs.

- State assumptions explicitly before implementing. If uncertain, ask.
- If multiple interpretations exist, present them — don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop, name what's confusing, ask.

## 2. Simplicity first

Minimum code that solves the problem. Nothing speculative.

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If it could be a third as long, rewrite it that short.

## 3. Surgical changes

Touch only what you must. Clean up only your own mess.

- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even where you'd do it differently.
- If you notice unrelated dead code, mention it — don't delete it, unless
  asked (this repo tracks such things as audit findings, e.g. `F10`'s dead
  auto-route branch in `INDEPENDENT_AUDIT.md`).
- Remove imports/variables/functions that YOUR change made unused. Don't
  remove pre-existing dead code unless asked.

The test: every changed line should trace directly to the request.

## 4. Goal-driven execution — this project's version is golden rule 7b

**"A green check is not evidence until it can go red."** Every new test
assertion must be run against the pre-fix code and shown to fail before it
is trusted against the fix. This project does this literally (sabotage the
fix, re-run, confirm red, restore, re-run, confirm green) — see any
`tests/test_v0*.js` file's own commentary for examples, or `docs/DEVELOPER_GUIDE.md`'s
account of `test_session_restore.js` and `test_v020.js`/`test_v021.js`.

For multi-step work, state a brief plan first:
```
1. [Step] -> verify: [check]
2. [Step] -> verify: [check]
```

## This repo's own non-negotiables (see docs/DEVELOPER_GUIDE.md §2 for the full list)

Restated here because they are the most commonly missed:
- Never hand-edit `complementtdm.html` — it is generated by `build.mjs`.
- `src/version.js` and `package.json`'s version move together, every time.
- `npm test` and `node tools/verify_control_streams.mjs` must both pass
  before anything is considered done.
- The app never suggests, recommends, or optimizes a dose or interval.
- Time is in days everywhere in the engine; never pass epoch-milliseconds
  into `runFit`/`buildGrid`.
